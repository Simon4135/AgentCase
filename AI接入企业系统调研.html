0先看结论：一句话回答「外面的世界怎么做的」

如果你只想记住一件事，就是这个。

结论：WorkBuddy 走的是「把文件扔进来 → 提示词 + 技能包 → 出文件」的外挂型路线，不碰企业系统； 而外面世界的 2025–2026 主流答案只有一条 —— 把企业系统用 MCP（Model Context Protocol，模型上下文协议）包成「工具」，让 Agent 直接调用。 这条路上已经有 ① 厂商官方（SAP / Salesforce / Dynamics 365 / Workday / ServiceNow / NetSuite / X）出原生 MCP Server； ② 连接器层（Composio / Zapier MCP / n8n / Workato / AnythingMCP）把成千上万个业务 API 变成工具； ③ 开源 ERP 自建（Odoo / ERPNext / 金蝶云星空 / ERP5）已能实测「17 秒查到库存、22 秒出财务表、直接审核单据」。 两者不是替代关系：外挂型解决「零改造、当天能用」，MCP 型解决「实时、可写、可审计」。真正的分水岭是你是否愿意动企业的系统。

2四条技术路线：从「不改系统」到「住进系统里」

外面世界的做法不是一种，而是四层。越往下，能力越强、改造代价越大。

路线 A · 文件投喂（外挂型）

代表：WorkBuddy 693 方案 / ChatGPT 上传 / Claude Projects

  • 系统完全不动，人工导出 Excel/PDF/截图
  • 当天可用、零 IT 参与
  • 数据是「某一刻的快照」，读不到实时、写不回系统
  • 不可审计、不可追溯来源

路线 B · 只读查询（MCP / API）

代表：IQMS 只读 MCP / 厂商 Hosted MCP Server

  • 把系统按只读权限包成工具，Agent 直接查
  • 实时数据、可审计，风险最低
  • 需要开 API / 建 Server，但不必改业务逻辑
  • 多数企业落地从这一层开始

路线 C · 可写执行（带人类审批）

代表：金蝶 k3cloud MCP / ERP5 / CoolERP 记账

  • Agent 能建单、过账、审核、改状态
  • 必须叠加权限分级 + 审批兜底 + 审计留痕
  • 需要处理幂等、回滚、并发与人机边界
  • 风险与价值同时最高

路线 D · 嵌进系统 / 无 API 兜底

代表：钉钉悟空路线 C / RPA：UiPath、Skyvern、browser-use

  • 反向把 Agent 嵌进自家 CRM 页面里（用户无感）
  • 或用 RPA / 浏览器自动化操作没有 API 的老系统
  • 适合「改不动系统」又「必须动数据」的场景
  • 稳定性差、维护成本高，属兜底手段

① Rivian × AWS for SAP —— 为什么财务流程塞不进硬编码脚本

来源：AWS for SAP 官方博客（aws.amazon.com/blogs/awsforsap/…）

Rivian 用 Amazon Bedrock AgentCore 自动化月末/季末结账文档、资源预测与供应商准入。官方博客给出的痛点原文极具代表性：传统自动化（硬编码脚本）解决不了财务流程，因为业务逻辑太动态——PO accruals（采购订单预提）要按金额阈值、PO 特性、交期、GAAP 条件规则去解释 SOP，编码进去可能需要上千行 if-then-else，且业务规则一变就要开发介入。

GenAI Agent 能直接读自然语言 SOP、按情境决策，规则变了不用重写程序。——这正是「文件 + 提示词」路线做不到、而「读系统 + 执行」路线才能做到的事。

同系列另有 Covestro 用 AWS 上 AI Agent 改造主数据治理（Master Data Governance），以及方法论文《Transforming ERP Business Process Operations with Agentic AI》。

② 金蝶云星空 × 灵基（KingdeeMCP）—— 中国 ERP 的实测四场景

来源：金蝶官方社区 vip.kingdee.com/article/879867537130394112（2026-08-25）+ 开源项目 WaHaiLong/KingdeeMCP（110★，Python，97 个工具）

在设置面板添加一个名为 k3cloud 的 MCP 服务器即完成连接，原文称「没有中间件配置，没有接口联调，不需要 IT 部门排期」，连上后拥有直接读写星空 ERP 数据的能力。四个实测场景：

① 查库存 17 秒 ② 查未关闭订单 7 张筛出 2 张 ③ 财务月度分析 22 秒 ④ 审核单据 真的调接口通过

① 问「查一下物料智能手机-6S 的即时库存」→ 自动查到物料编码 S1.06，按仓库分拆（手机成品仓 22 台、电商总仓 98 台，合计 120 台），与星空界面逐行核对分毫不差。
② 问「查询客户金蝶东方集团的所有销售订单有多少张未关闭的」→ Agent 自己摸清关闭状态字段含义（A=未关闭，B=已关闭），筛出 7 张已审核订单、其中 2 张未关闭。
③ 问「统计每月销售额…除了金蝶香港组织，按价税合计本位币计算，每月同比上月增加多少」→ 自动识别组织字段、排除编码 104 的香港公司、保留蓝海销售与蓝海电商，算出 1 月合计 601,186 元与 2 月环比。
④ 说「帮我审核一张费用申请单，申请人是 XXX」→ 查出待审核单据、逐张查看详情锁定李忠声那张 800 元单据、调用审核接口通过，并提示还有一张 500 元待审核。文中还提到它会把 API 调用经验存进记忆，下次不用重新摸索。

技术栈：FastMCP（Python）。这是国内开源生态里与 WorkBuddy 场景最接近、但路线完全相反的样本——同一批业务问题，一边靠导 Excel，一边靠直连 ERP。

③ 制造业 ERP（IQMS / DELMIAworks）—— 一个人做的只读 MCP，一年省 300 小时

来源：haydennester.com/case-studies/iqms-mcp（个人实战记录）

底层 Oracle，系统有 1,500+ 张表。作者 map 了 1,587 张表、2,959 条外键关系，建了一个只读 MCP Server（SSE transport、Oracle python-oracledb、Claude Opus/Sonnet、把 schema 预载入 Agent 上下文、内网部署不外泄）。

覆盖表 1,587 外键关系 2,959 作者自述年省 约 300 小时 ≈ $14K 分析师人力 写权限 设计上为零

把工厂里的问题从「写 SQL 或等厂商报表队列」变成秒级回答。文章还专门解释了「为什么用 MCP 而不是做一个 Text-to-SQL 应用」。

④ Claude 连真实 ERP 记账 —— 「AI 跑在系统记录源里，而不是描述它」

来源：aicoooffice.substack.com（2026-06-24，作者 Joost Vogelezang）

把 Claude 通过 MCP 连到一个叫 CoolERP 的真实 ERP demo。作者强调的三个「不是…而是…」：模型不是总结试算表，而是拉取它；不是描述 COGS 科目，而是下钻；真的过账了一张 journal entry（日记账分录）。

最有说服力的细节是反向验证：故意过一张不平的凭证时，ERP 拒绝接受。作者原话——「AI working inside the system of record with typed, governed tools and full audit visibility」（AI 运行在系统记录源之内，用的是有类型、受治理的工具，全程可审计）。

这个案例说明了可写路线的安全边界在哪里：不是让模型自己保证正确，而是让 ERP 的校验规则挡住错误。

⑤ Workato × Anthropic —— 8 个月 800+ 个 MCP Server

来源：claude.com/customers/workato（Anthropic 官方客户案例页）
员工采用率 7 倍 8 个月建 800+ 个自定义 MCP Server 其中最后一个月 150+ 底层连接 14,000+ 应用 预建 workflow 900,000+

Workato 提供 100+ 全托管 MCP Server 模板，把 Claude 连到 Salesforce / NetSuite / Workday 等。案例页给出的关键数字是「部署 MCP server 后员工采用率提升 7 倍」——说明真正的瓶颈从来不是模型能力，而是「能不能动到数据」。

⑥ Nexedi ERP5 —— 开源 ERP 官方自带 MCP，能建采购单

ERP5 的官方 MCP Server 允许任何 MCP client（Claude、Open WebUI、Continue 或自写脚本）连到运行中的 ERP5 实例做 search / read / create / edit / validate documents / run reports，甚至开发 ERP 本身。文档提出「HATEOAS toolset」（超媒体即应用状态引擎风格的工具集）设计，示例动作就是「Create a purchase order for project Y with 1 quantity of this product」。

⑦ Block（Goose）—— 从「一次性定制集成」到「8 周铺满全公司」

来源：aviator.co 播客（2025-12-11），嘉宾为 Block VP of Engineering Angie Jones

Block 的 Goose 是最早的 MCP client 之一，起点是 ML 工程师 Bradley Axton 的内部实验。转折点在于：工程师们想连各种内部系统，但当时每个集成都是一次性定制的（bespoke one-off）；于是他们找 Anthropic 拿到早期 MCP 规范、把 Goose 重写成 MCP client 并开源，8 周内把 AI Agent 推广到公司每个部门。

这条经验的普适价值：集成的边际成本决定 Agent 的扩散速度。一对一写连接器，就只能服务一个部门；抽象成协议，才能铺满一家公司。

⑧ 中国制造业的「系统内嵌」实践：飞鹤、美的

来源：快科技报道（2026-08-27，飞鹤）/ itcn.cc（2026-01-20，美的美云智数）

飞鹤 × 火山引擎 HiAgent：10 余家智能工厂、数字化生产设备占比超 90%；已开发 436 个智能体，近三个月活跃用户超 24 万，Tokens 消耗接近 230 亿。其 AI TPM（智能化设备管理操作系统）基于飞鹤 EV 设备管理系统 + HiAgent + Hermes 智能体框架。

覆盖工厂 9 家 故障恢复时长 104h → 47h 重复故障率 34% → 8% 服务工程师 千余名

飞鹤 AI 负责人原话：「效果最明显的场景，一般不是那些比较炫酷的，而是高频的、重复的、数据基础比较好的、能够嵌入到我们业务流程中的场景。」——这句话几乎可以直接当作 WorkBuddy 选型指南的注脚。

美的 / 美云智数：推出制造 AI 智能体（美擎 TPM / DMS / LOSS / 模具），与 MES、EAM/TPM、SCADA、QMS 等业务系统及现场 PLC、AGV、传感器打通，底座是「企业数据银行」+ 多域知识库。落地证据：美的荆州洗衣机智能体工厂获 WRCA 认证；美的厨卫电器（芜湖）工厂为世界经济论坛 2026-01-16 新晋灯塔工厂，部署 113 个数字化用例、其中约 35% 由 AI 驱动，实现交货周期缩短 39%、库存周转天数减少 30%、市场缺陷率下降 86%。

这两家与 WorkBuddy 的根本区别：它们啃的是「与业务系统打通」这块硬骨头，所以代价是数年投入与专职团队，收益是可量化的产线指标。

⑨ 一条务实的分档建议：钉钉悟空的 A / B / C 三路线

来源：开沿科技《钉钉悟空 API 接入 ERP 集成》长文（2026-06-14）

文中给了一个 80 人鞋服批发企业的真实翻车现场：开通悟空一个月，销售在群里 @ 悟空问「这个客户上个季度发了多少货」答得头头是道，但只能基于上传的知识库回答，查实时库存、回款、在途订单一概不知。

据此给出的三条路线与选择逻辑：路线 A 原生 Skill 包装（ERP 有标准开放 API 时写薄中间层，投入小上线快，以查询类为主）；路线 B 自定义 Skill 写动作（提交报销、创建客户、生成调拨单——难点在权限、审批流、防误操作，「不能让 Agent 随便代下游员工签字」）；路线 C 反向把 Agent 嵌进自有应用（CRM 详情页右侧放对话区，用户感知在自家系统内完成，对话流可在自家留痕）。

最容易翻车的地方：把所有数据怼进知识库 → 静态文档答得准、动态业务数据全是幻觉。正确分工是静态慢变内容走 RAG（检索增强生成），实时业务数据走结构化查询。

规模参照：McKinsey《The State of AI: Global Survey 2026》——年收入超 10 亿美元的大型组织里，40% 表示正在规模化使用 AI Agent，高于去年的 27%；但小型企业基本持平在 22%。该文与多个分析一致指出：差距来自实施能力，不是软件成本。

6为什么大部分 Agent 项目卡住：失败的真正原因与安全边界

这一节回答「那为什么不都去做？难在哪？」——也直接解释了 WorkBuddy 为什么要选择外挂路线。

口径必须先分清（否则数字会骗人）

「88%」「89%」「95%」「40%」这些数字经常被混用，但它们测的根本不是同一件事。据 alatirok.com 的逐条溯源：

  • 40% — Gartner：预测到 2027 年底超过 40% 的 agentic AI 项目会被取消。唯一真正针对 Agent 的权威数字
  • 88% / 89% — 多个来源引用的「Agent 试点未进生产」比例，AWS 官网 banner 原文也在用「88% of agent pilots stall」。口径为试点阶段
  • 95% — MIT 的生成式 AI 试点研究，测的是 GenAI 试点而非 Agent。不可直接套用
  • 41% — Stacklok：软件组织中已进入 MCP 生产阶段的比例。正面口径
  • 40% vs 22% — McKinsey 2026：大企业（>10 亿美元营收）规模化使用 Agent 的比例 vs 小企业。能力差距

卡点排序：不是模型不行，是集成不行

  • 第一名：集成。dynamisch.co 直接把文章命名为《The Integration Wall》（集成墙），主张失败主因是集成而非模型能力。
  • 第二名：认证与授权。agent 从「单用户 demo」走向「多用户企业部署」时认证最先崩——原型可以用环境变量或共享 service account，生产必须做委托授权、凭据隔离、策略执行与审计追踪。
  • 第三名：上下文成本。Anthropic 实测 5 个 Server 的工具定义就要吃掉 55K tokens；工具搜索与代码执行等优化可削减 85%–99.9%。GitHub 甚至把自己家的 MCP Server 换成 gh CLI 来做数据抓取。
  • 第四名：权限与「越权代签」。不能让 Agent 随便代下游员工签字——这是写权限路线必须挡住的坑。

认证为什么会先崩：Agent 引入的新身份问题（Arcade.dev《7 Best AI Agent Authentication Platforms (2026)》核心论点）

风险原意后果
Credential drift（凭据漂移）原型期的共享密钥被沿用到生产无法区分「是谁让 Agent 做的这件事」
Confused deputy（混淆代理）Agent 拥有高权限，用户通过间接提示注入借它之手越权AI 成了「有权限但被骗」的执行者 —— 2026 年最被反复讨论的攻击面
过宽 API key一次授权覆盖所有租户/所有动作越权读取、跨系统数据外泄
限流冲突多 Agent 共享同一凭据配额互相挤兑，生产不稳定
策略不一致同一动作在不同入口判定不同审计无法解释
耐久模式：「两个身份 + 委托上下文」。不是给 Agent 一个万能身份，而是同时携带 Agent 身份 与 用户身份，并在运行期评估一个任务级授权上下文（task-specific authorization context），每次动作都取权限交集。
延伸阅读：OWASP 的 MCP Security Cheat Sheet 与 MCP Tool Poisoning 条目；微软 MCP-SECURITY-GATEWAY-1.0 规范；arXiv 2511.20920《Securing the Model Context Protocol (MCP): Risks, Controls, and Governance》——该文把攻击面分成数据驱动（用户生成内容注入、跨系统外泄）、供应链（registry 信任、rugpull 攻击、通过工具描述做上下文投毒）、配置治理（过度授权、动态工具发现）、运行安全（PII 合规、密钥暴露、多 Agent 监控层威胁）四类，并特别提到一类对手：善意但出错的 Agent 自己。

关键判断（请允许我说得直白）：这不是「WorkBuddy 落后」——这是一次刻意的取舍。它把「企业改造」这一项成本从方案里彻底删掉，代价是把「实时、可写、可审计」三项能力也一并删掉了。 对 一个 200 人以下、IT 只有一个兼职、ERP 是五年前买的 的企业来说，这个取舍是对的：外面那套 MCP 集成要 5–15 个工作日 + 身份权限设计，而这套方案当天下午就能跑出结果。 但如果企业已经有 API、有人、有合规要求，那就应该走 MCP 路线，因为「导出 Excel 再上传」在那种环境下反而变成新的风险点——数据副本散落、口径不一致、无审计。

8如果你要往前走一步：按优先级排的行动清单

从「今天就能做」到「需要立项」，按代价从小到大。

第 1 步 · 今天（零成本）

  • 先把 WorkBuddy 的 693 个方案用起来——它是零改造路线的天花板
  • 挑第一个场景：打开 索引.html，按自己的角色筛选，看「最大差异点」是否正好是你的痛点
  • 把「高频、重复、数据基础好」的三条作为选型硬标准

第 2 步 · 本周（验证）

  • 盘一下：你常用系统里哪些有开放 API（金蝶、用友、钉钉、企微、飞书大多有）
  • 装一个 MCP 客户端（Claude / Cursor / Cherry Studio 等），先连一个只读的官方或社区 MCP Server 试手感
  • 读一遍 OWASP 的 MCP Security Cheat Sheet，知道攻击面长什么样

第 3 步 · 本月（试点）

  • 选一个「读多写少」的场景做只读 MCP 试点（参考案例③：先只读，写权限设为零）
  • 老系统没 API？用 AnythingMCP 这类网关把 REST/SOAP/GraphQL/OData/SQL 直接转成工具
  • 为每个 Agent 建立独立身份 + 委托上下文，不要复用共享密钥

第 4 步 · 立项（写权限）

  • 只做「Agent 出草稿 → 人点确认 → 系统执行」的三段式，绝不让 Agent 直接落库
  • 把审批流、权限分级、审计留痕当前置条件而不是后续优化
  • 用系统的校验规则兜底（参考案例④：不平的凭证被 ERP 拒绝）
  • 衡量指标对齐飞鹤那句话：高频、重复、数据基础好、能嵌进流程
