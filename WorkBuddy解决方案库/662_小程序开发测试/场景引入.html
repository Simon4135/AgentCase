一这件事现在是什么样

餐饮品牌开发人员 · 每个小程序都从零搭一遍

某连锁餐饮品牌，门店要上一个扫码点餐小程序。开发排期表上写着三周 —— 第一周搭环境、搭项目结构，app.json、pages、components 一个个手写；第二周写页面，五个页面里有三个和上一个项目长得差不多，照样重写一遍，Mock 数据一条条编；第三周补测试，时间不够，测试用例只覆盖了主流程，边界情况「先上线再说」。到了发布前，隐私协议、类目要求、AppID 配置挤在一起，返工两次才过审。店长问「扫个码点餐要做三周？」，开发只能苦笑 —— 活不难，难的是每个项目都把同样的活重做一遍。

二痛点 · 每条都发生在昨天

不是流程描述，是开发团队每个项目真实上演的日常 —— 以下案例均取自场景调研与演示素材

1
页面组件手写重复：菜单页、购物车、订单页 —— 每个项目结构雷同，照样逐行重写
2
测试覆盖率低：排期一紧，测试就只剩「主流程点一遍」，边界条件与异常场景没人补
3
开发环境搭建耗时长：项目结构、Mock 数据、工具链配置，开工前先搭两三天
4
发布前检查项多且散：隐私协议、类目要求、包体积、API 兼容性 —— 漏一项就驳回，驳回一次等三天

三换个做法之后

变化不在「快」，在「交付即可跑、测试跟着代码一起出」

✕ 现在的做法

  • 项目结构、页面、组件从零手写，重复劳动占一半工时
  • Mock 数据逐条编，编错一个字段调半天
  • 测试排期被压缩，用例只覆盖主流程，边界靠上线后用户踩
  • 发布清单凭记忆核对，隐私协议漏一项就被驳回

✓ 交给 Agent 之后

  • 需求解析输出确认清单，架构设计一次出齐项目结构与数据流
  • 逐页面生成 WXML/WXSS/JS/JSON 四件套 + 组件 + Mock 数据，导入开发者工具即可运行
  • 功能/兼容性/性能三项测试随代码一起产出，报告直接可看
  • 发布清单与隐私协议模板备好，调试修复后输出可提交审核的完整代码包

四场景闭环

6 步 · 每一步的产出都是下一步的输入

第 1 步
需求解析 · 确认清单先行识别目标平台/业务场景/功能列表，输出需求确认清单 —— 做什么、不做什么，先对齐再动手
第 2 步
架构设计 · 结构一次定好设计项目结构（app.json + pages + components + utils），规划页面导航流程与数据流，输出架构概览
第 3 步
编码实现 · 四件套逐页生成逐页面/组件编写完整代码（WXML/WXSS/JS/JSON），内嵌 Mock 数据支持独立运行
第 4 步
功能测试 · 逐页面过交互逐页面验证核心交互流程，输出测试用例与功能测试报告
第 5 步
兼容与性能检测 · 双报告检查 API 兼容性/机型适配/安全区域；检查包体积/setData 频率/图片压缩/首屏指标
第 6 步
调试修复与发布准备基于测试结果修复问题；生成发布清单与隐私协议模板，输出可提交审核的完整代码包

要准备什么

需求描述（一句话或需求文档，Word / Markdown / 纯文本）
「帮我开发小程序」或描述功能需求均可
品牌菜单与门店信息（可选）
有则生成真实业务感的 Mock，无则用通用虚构数据
发布约束（类目 / AppID 由谁配 / 隐私协议口径，可选）
有什么给什么 —— 缺项按模板口径处理并标注

为什么这个场景值得做

痛感 4 × AI 适配 5 ÷ 落地难度 2 = 10.0

最大差异点 · 从需求描述直接到可运行代码包：页面、组件、Mock、测试报告、发布清单一趟出齐 —— 过去数周的活，数小时拿到发布就绪的版本。

评分口径：痛感看「这事没做好谁会生气、生气到什么程度」； AI 适配看「输入是否非结构化、是否要跨渠道取数、错了能不能当场看出来」； 落地难度是分母 —— 需要先对接 POS/ERP 才能用的场景，分数会被压得很低。

五会产出什么

判断标准只有一个：这份东西导入开发者工具能不能直接跑

正式件本体
小程序项目代码包
完整目录结构 + 页面代码 + 组件 + Mock 数据 · 可直接导入开发者工具运行
质量件
测试报告（功能 / 兼容性 / 性能）
三份 Markdown 报告 · 测试结果与优化建议直接可查
发布件
发布清单 + 隐私协议模板
提交审核前的检查项逐项列清 · 协议模板待法务复核

这套东西不承诺什么

不替代微信官方审核，不处理真实支付对接，不内嵌真实业务数据与凭证；AI 生成代码可能存在安全漏洞或不符合最新小程序规范，开发主管须复核代码安全性与 API 兼容性；自动测试用例以核心交互为主，边界条件与异常场景须开发人员补充；隐私协议与用户协议为模板，发布前须法务复核并适配类目要求；产物代码须适配 AppID/域名/业务资质后发布，非零修改直接上线。
