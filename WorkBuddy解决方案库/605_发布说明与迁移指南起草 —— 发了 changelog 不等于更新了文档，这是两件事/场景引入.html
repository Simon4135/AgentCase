三换个做法之后

变化不在「快」，在「参与的角色」和「覆盖的范围」

✕ 现在的做法

  • 「发布 changelog 条目和更新参考文档是两件不同的事——团队普遍做了第一件就当完成了」
  • Breaking change 标准管理：迁移期最低 6-12 个月（Stripe 用 12 个月）、Sunset/Deprecation 响应头做机器可读通告——而多数团队的迁移期是「发完就算」
  • 「没有 changelog 的 API 在向开发者广播：我们随时可能弄坏你、我们不追踪自己的变更」——发布说明的欠账直接变成集成方的信任折损
  • 金融 API 里错误示例会转错钱且不可撤销——迁移指南里的示例代码质量是运营事故级风险

✓ 交给 Agent 之后

  • 多来源文件一次读入，先做口径与完整性校验，再开始算
  • 每条结论绑定来源文件、字段或条号，可以被审
  • 产出是企业真会流转的正式件（带签批栏），不是一张展示用的表
  • 该拦的地方给出「现在还不能提交」，并给不用干等的替代方案

四场景闭环

5 步 · 每一步的产出都是下一步的输入

第 1 步
变更分类登记本版全部变更按 Added/Changed/Deprecated/Fixed/Security 五分节归类
第 2 步
Breaking 判定与影响挂接逐条判定是否 Breaking；是则挂受影响集成方与端点级 diff
第 3 步
迁移指南起草端点级变更说明 + 迁移示例（逐条验证）+ 弃用时间表建议
第 4 步
三受众分别成稿客户版/开发者版/客服支持简报——同一事实三种讲法
第 5 步
发布包汇编与签发流转三件套 + 通知范围建议，签发栏留空

为什么这个场景值得做

痛感 5 × AI 适配 3 ÷ 落地难度 2 = 7.5

最大差异点 · 发布包三件套面向三个受众分别成稿，不是一份文档改三遍格式：客户版讲「对你的影响」（无技术术语）；开发者版讲「怎么迁」（端点级 diff + 验证过的迁移示例 + 弃用时间表）；客服版讲「客户会来问什么」（预判问题清单 + 应答口径）。原料直接来自 API 文档与代码同步巡检 的漂移台账与合并记录，不重新考古。

评分口径：痛感看「这事没做好谁会生气、生气到什么程度」； AI 适配看「输入是否非结构化、是否要跨部门取数、错了能不能当场看出来」； 落地难度是分母 —— 需要客户先做数据治理的场景，分数会被压得很低。

这套东西不承诺什么

迁移指南的代码示例必须逐条经过可运行验证，未验证示例标注「草稿」；弃用时间表只起草建议（对照行业惯例给区间），正式承诺由产品与技术负责人签发；客户通知的发送范围与时间由客户成功确认，本场景只出材料不出发送动作。
