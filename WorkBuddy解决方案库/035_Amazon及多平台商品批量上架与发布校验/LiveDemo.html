旧 ERP 在 2024 年把 K09 的颜色建成独立 SKU，映射表无人维护但仍在生效——ERP 按旧规则生成父子体，平台当然报错。

这一步的看点 · 那份「没人维护但还在生效」的表旧映射表是两年前ERP迁移时留下的，全公司没人记得它还在参与刊登逻辑。林蔚在回执层面改了两天没解决，因为错的不是回执，是规则。Agent 把旧表翻出来，24 个变体错误找到了同一个根。历史遗留数据不会自己消失，它只会在你最忙的时候跳出来。

4

分批发布 · 不是全对才发，也不是全发

无争议先发 · 争议修正后重试
批次SKU前置条件预计时间
第一批HT-L10 三个变体图片重传 1000px 后当天
第二批HT-K09-BLK / WHT旧映射表停用 + 父子体重建+1 天
第三批HT-K09-GRN类目修正 + 属性模板重填+2 天

每批发布留存回执：成功/失败/警告分别入队，失败项进入修正队列而不是重新全量发。

这一步的看点 · 该停的地方停下来林蔚原本的计划是「全改完一起发」——那是再等三天。Agent 把 6 个 SKU 拆成三批：没有争议的今天先上线跑数据，有争议的改完再发。发布不是二元动作，是可以分批的风险管理。
⚠ Agent 的结论：变体映射未确认前，不能批量发布
旧 ERP 映射表仍在生效，直接全量发布会把 K09 父子体再次挂错——拆错一次，修复要重建父体并等待平台重新索引。

但新品等不了三天全改完，所以 Agent 给了两个方案 ——
方案一：今天先发 HT-L10 三个无争议 SKU（图片重传后即可），先跑数据；
方案二：停用旧映射表、修正类目后全量一次发（慢 2 天，但避免分两批的流量爬坡差异）。

同时自动生成：《上架字段修正对照表》（42 个错误逐项对照+三批发布计划+签批栏）。

发布按钮留给人 —— 变体关系由林蔚确认后才执行。

追问

现场可能被问到的

答不上来的问题比答得漂亮的问题更能决定演示结果
·
ERP 不是也能自动刊登吗，为什么还要这个？ （IT/运营常问）ERP 执行刊登，不判断主数据对错。42 个错误 ERP 也报给你了，但「为什么是这 42 个、根因在哪、先改哪个」要跨主数据、旧规则、平台 Schema 三处对照——这正是 ERP 之外的那层。
·
为什么不直接用 AI 重新生成所有 Listing？ （运营常问）生成文案解决的是「写什么」，这里的问题是「主数据规则冲突」——文案写得再好，父子体挂错照样发不出去。先修数据，再谈文案。
·
平台 API 不是有校验吗，为什么还要前置校验？ （IT 常问）平台校验在发布时告诉你错了，前置校验在发布前告诉你哪错、怎么改、先改哪个。区别是改三轮还是改一轮。
