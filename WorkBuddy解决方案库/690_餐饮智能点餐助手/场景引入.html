一这件事现在是什么样

消费者 · 想吃一顿划算的饭，要先过三道关

周五中午，写字楼下的午餐高峰。一位顾客想点杯咖啡：打开品牌 App 翻菜单 5 分钟还没定下来喝什么；想起好像有张优惠券，翻完卡包翻小程序，比对半天不知道用哪张最划算；换一家品牌，以上流程重来一遍。而在品牌的另一侧，运营人员每接入一个新渠道就要重复开发一遍点餐对接 —— 菜单、优惠、订单接口各不相同，IT 团队的排期排到了下个季度。

二痛点 · 每条都发生在昨天

不是流程描述，是顾客与品牌团队每天真实上演的折腾 —— 以下案例均取自场景调研与演示素材

1
点餐决策耗时长：翻菜单 5 分钟起步，口味、预算、人数、营养每样都要自己权衡
2
优惠信息散落各渠道难比对：可领券、已领券、门店可用券各在一处，用哪张最划算全靠人肉比价
3
每个品牌单独对接，重复开发：菜单、优惠、订单接口各不相同，新渠道接入排期以季度计
4
价格库存不实时，下单心里没底：看到的优惠用不了、想点的已售罄，下单前总要反复确认

三换个做法之后

变化不在「快」，在「一句话走完全链路」和「接入零代码」

✕ 现在的做法

  • 翻菜单 5 分钟起步，偏好全靠自己权衡
  • 优惠券翻卡包人肉比价，用错券是常态
  • 新品牌接入重写一套对接，排期以季度计
  • 价格库存以 App 为准，来回切换反复确认

✓ 交给 Agent 之后

  • 一句话说偏好，规则引擎排序推荐并附推荐理由
  • 可领/已领/门店可用券一起查，对比有券无券价格，自动推荐最省方案
  • 新品牌在 brands.json 追加一条配置即接入，零代码扩展
  • 下单前二次确认（门店/商品/优惠/金额/取餐方式），异常价格停止下单

四场景闭环

6 步 · 每一步的产出都是下一步的输入

第 1 步
品牌识别与路由 · 解析品牌关键词读取 brands.json 匹配品牌 → MCP 工具前缀，自动路由到对应 MCP 服务
第 2 步
门店查询与选择 · 附近的店先摆出来调用品牌 MCP 门店查询工具（支持 IP 定位/地址搜索），展示附近门店让用户确认
第 3 步
菜单浏览与智能推荐 · 偏好驱动排序获取品类与商品列表；用户表达口味/预算/人数/营养偏好时，基于规则引擎排序推荐并附推荐理由
第 4 步
优惠券查询与最优选择 · 最省方案自动算查询可领券/已领券/门店可用券，对比有券无券价格，推荐最省方案
第 5 步
下单与支付确认 · 二次确认不省略下单前二次确认（门店/商品/优惠/金额/取餐方式），返回支付链接与截止时间
第 6 步
订单跟踪与售后 · 状态随时查查询订单状态/取餐码/预计时间，如需取消按品牌能力处理

要准备什么

自然语言点餐需求（如「帮我点一杯瑞幸拿铁」）
品牌名 + 点餐/优惠/查单意图即可
偏好信息（可选）
口味/预算/人数/营养目标
品牌 MCP 配置（前提条件）
至少配置一个品牌 MCP Server（瑞幸 lk-order 或麦当劳 mcd-order）并完成连接器信任，Token 由用户自行获取

为什么这个场景值得做

痛感 4 × AI 适配 4 ÷ 落地难度 3 = 5.3

最大差异点 · 差异不在对话体验，在接入成本：新品牌只需在 brands.json 追加一条配置（品牌名/别名/MCP 前缀/价格单位/工具映射），零代码扩展 —— 点餐全链路一套 Skill 通用。

评分口径：痛感看「这事没做好谁会生气、生气到什么程度」； AI 适配看「输入是否非结构化、是否要跨渠道取数、错了能不能当场看出来」； 落地难度是分母 —— 需要先对接 POS/ERP 才能用的场景，分数会被压得很低。

这套东西不承诺什么

不替代用户最终支付确认，创建订单前必须二次确认、支付链接醒目展示；不处理品牌 MCP 未暴露的能力（退款/投诉）；不保证所有品牌 MCP 功能完整可用；价格/优惠/库存以品牌 App 实际为准、非实时担保，大额订单建议二次核实；不保存/打印/转发 MCP Token、手机号、地址、订单号等敏感信息；新品牌接入需用户自行配置 MCP Server，本 Skill 不提供 MCP 凭证获取服务；推荐结果仅供参考，不构成消费建议。
