### 一、这件事现在是什么样

*研发与开发者文档 · 真实业务触发*

优选百货的集成联调群炸了：客户开发者按文档示例调 `/settlement/reconcile`，返回的 `amount` 字段在文档里是字符串、实际是数字，联调直接报错——排查发现该端点在 v2.1 灰度中改了返回结构，文档站还停在 v2.0；技术负责人要求本周内给出「还有多少个端点是这样的」的完整答案。

### 四、场景闭环

*5 步 · 每一步的产出都是下一步的输入*

第 1 步
端点清单对齐文档站 × 规范 × 代码三方取并集，缺文档的端点单列
第 2 步
逐端点漂移检测参数/返回结构/示例代码/状态码四类漂移逐条登记
第 3 步
影响面挂接每条漂移联到「哪些客户在用」（联调工单+集成登记表）
第 4 步
修复优先级排序客户在用的漂移优先，无客户的进待办池
第 5 步
巡检报告与修复任务派发逐端点清单 + 修复建议 + 派发状态，周度滚动

    要准备什么
API 文档站全量（或核心端点文档导出）
63 个端点的当前文档态——漂移的一方

OpenAPI/Swagger 规范文件
理想态基准——有规范就能机读对照（没有则标注退化路径）

近期合并记录与发版说明
v2.1 灰度改了哪些端点——漂移的另一方

客户集成联调工单
谁在用哪个端点——影响面与修复优先级的依据

    为什么这个场景值得做

      痛感 4 × AI 适配 4 ÷ 落地难度 2 = 8.8

      最大差异点 · 不是「帮开发者写文档」：巡检的输入是文档站、OpenAPI 规范、近期合并记录三方对照，输出是逐端点的漂移清单（参数/返回/示例/状态码四类漂移）+ 每条的影响面（哪些客户在用这个端点——来自联调工单与集成登记表）。修复优先级按「客户在用的漂移优先」排，而不是按发现顺序排。

      评分口径：痛感看「这事没做好谁会生气、生气到什么程度」；
      AI 适配看「输入是否非结构化、是否要跨部门取数、错了能不能当场看出来」；
      落地难度是分母 —— 需要客户先做数据治理的场景，分数会被压得很低。
