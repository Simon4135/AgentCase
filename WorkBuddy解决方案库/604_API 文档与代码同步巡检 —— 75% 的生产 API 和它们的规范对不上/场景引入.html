三换个做法之后

变化不在「快」，在「参与的角色」和「覆盖的范围」

✕ 现在的做法

  • 47% 的组织承认 API 文档与实际实现不同步、只有 5% 认为自己的文档「非常好」；「没时间」是文档质量最大障碍
  • 39% 把「文档不一致」列为最大协作障碍；44% 的开发者只能直接翻源码来理解 API 行为；68% 认为过时文档是最大挫败
  • 75% 的生产 API 与其 OpenAPI 规范存在实测偏差；71% 的开发者曾因更好的文档而弃用一个 API——文档就是产品的销售页
  • 技术写手与开发者的真实配比从 1:12 到 1:200——靠人力追代码变更速度在数学上就不成立

✓ 交给 Agent 之后

  • 多来源文件一次读入，先做口径与完整性校验，再开始算
  • 每条结论绑定来源文件、字段或条号，可以被审
  • 产出是企业真会流转的正式件（带签批栏），不是一张展示用的表
  • 该拦的地方给出「现在还不能提交」，并给不用干等的替代方案

四场景闭环

5 步 · 每一步的产出都是下一步的输入

第 1 步
端点清单对齐文档站 × 规范 × 代码三方取并集，缺文档的端点单列
第 2 步
逐端点漂移检测参数/返回结构/示例代码/状态码四类漂移逐条登记
第 3 步
影响面挂接每条漂移联到「哪些客户在用」（联调工单+集成登记表）
第 4 步
修复优先级排序客户在用的漂移优先，无客户的进待办池
第 5 步
巡检报告与修复任务派发逐端点清单 + 修复建议 + 派发状态，周度滚动

要准备什么

API 文档站全量（或核心端点文档导出）
63 个端点的当前文档态——漂移的一方
OpenAPI/Swagger 规范文件
理想态基准——有规范就能机读对照（没有则标注退化路径）
近期合并记录与发版说明
v2.1 灰度改了哪些端点——漂移的另一方
客户集成联调工单
谁在用哪个端点——影响面与修复优先级的依据

为什么这个场景值得做

痛感 4 × AI 适配 4 ÷ 落地难度 2 = 8.8

最大差异点 · 不是「帮开发者写文档」：巡检的输入是文档站、OpenAPI 规范、近期合并记录三方对照，输出是逐端点的漂移清单（参数/返回/示例/状态码四类漂移）+ 每条的影响面（哪些客户在用这个端点——来自联调工单与集成登记表）。修复优先级按「客户在用的漂移优先」排，而不是按发现顺序排。

评分口径：痛感看「这事没做好谁会生气、生气到什么程度」； AI 适配看「输入是否非结构化、是否要跨部门取数、错了能不能当场看出来」； 落地难度是分母 —— 需要客户先做数据治理的场景，分数会被压得很低。

这套东西不承诺什么

巡检只对照「文档/规范/代码实际行为」三方给出漂移清单，不直接改文档——修复由研发在评审后执行；生产环境的实际行为验证只用只读调用，不碰数据；示例代码的核对以「可运行」为准，风格问题不进清单。
