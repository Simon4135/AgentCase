优选百货联调炸了：`/settlement/reconcile` 的 `amount` 字段文档写的字符串、实际返回数字。技术负责人要答案：还有多少端点是这样。 这是文档站 63 个端点的导出，这是 OpenAPI 规范，这是 v2.1 灰度以来的合并记录，这是联调工单和集成登记表。 帮我做全量巡检： 1. 逐端点对三方（文档/规范/代码），漂移按参数、返回结构、示例、状态码分类登记。 2. 每条漂移挂上影响面——哪些客户在用这个端点，工单里有没有已经在炸的。 3. 修复优先级按「客户在用优先」排，没客户的进待办池。 4. 文档和代码一致但示例跑不通的，单独挑出来——那是环境问题不是漂移，别混进来。 周度滚动，下周只报新增和修复的进出账。

漂移四分类、影响面挂接规则、Breaking 级判定在能力包里；现场需要的是文档站导出、规范文件、合并记录三样——没有规范的团队走退化路径（文档对代码直比）。

触发

文档站 63 端点对照代码 · 本周捞出 17 处漂移

文档与代码的对照从「想起来才查」变成每周固定动作

漂移不是事故，是默认状态——每一次「改端点但没改文档」的 PR都在制造漂移。巡检做的第一件事是让漂移有台账：新增几处、修复几处、还剩几处，肉眼可见地收敛。

这份巡检报告产出的是漂移清单与修复建议：改文档走研发评审，「改端点的 PR 必须同时改文档」这条规则由人来执行——工具负责盯住每一次漏网。

方案一：9 处客户在用漂移本周修完（负责人与期限已在清单），8 处无客户排下迭代、环境 3 处今天移交运维——联调群里当天可答「还有多少处类似」，内部只占研发 1 人本周约三成产能。

方案二：若 17 处一把全修——研发本周两人全部投入，客户在用的 9 处反而和无客户的 8 处一起排队；而续约在谈的优选百货联调等不到下迭代——修复顺序跟着客户影响走，不跟着发现顺序走。

追问现场可能被问到的

答不上来的问题，比答得漂亮的问题更能决定这场演示的结果

没有 OpenAPI 规范怎么办？
走退化路径：文档对代码直比，漂移照样能抓，只是精度从「字段级」降到「行为级」。巡检跑起来的第一份产出建议就是「先生成规范骨架」——从第二周起回到机读对照。
巡检能不能自动改文档？
不能也不建议。巡检产出漂移清单与修复建议，改文档走研发评审——「改端点的 PR 必须同时改文档」这条规则（业界已验证的路线）由人来执行，工具负责盯住每一次漏网。
