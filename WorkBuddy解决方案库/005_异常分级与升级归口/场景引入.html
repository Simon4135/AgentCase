一套引擎吃三种入口：客户投诉、现场停线、跨部门久拖。走同一套三级分级 → 建议归口哪个部门并说明为什么不是别的部门 → 输出可直接贴群的协调稿 + 对外话术 + 带SLA 的台账。这个场景的价值是"降级"和"归口"，不是"报警"。

二痛点

1
所有事都"很急"，于是没有事真的急 — 一线上报时倾向把问题说重：说轻了怕没人管，说重了至少有人看。结果群里每条都是"客户很生气""马上要停线"。老板一天要在二十几个群、几百条消息里自己判断哪条是真的要命，判断的依据往往只是谁的语气更急。真正的后果是资源被分散到不该占用它的事情上，而真正紧急的那条反而没人跟。
2
"这个问题上次也有过"——上次是什么时候、怎么处理的，没人说得清 — 判一件事该不该升级，最关键的一个维度是它是不是重复发生。第一次是意外，第三次就是管理问题。但"是否重复发生"在任何系统里都没有这个字段，只能靠人翻记录回忆。于是同一台设备半年漏三次油、同一个客户三次投诉同一个部位，每次都被当成新问题处理一遍。
3
跨部门问题的死法是"集体沉默" — 喷涂返工率高，生产说是来料板材有油污，采购说供应商检验报告都合格，品质说要工艺定标准，工艺说是设备喷房湿度不稳。每一方的说法都成立，所以每一方都不用负责。这类问题的本质不是某个部门失职，而是标准本身是空白的——但没有人有权限去指定"这个标准该谁定"，于是周会上提了三次，一次结论都没有。
4
升级上去了，但没带该带的东西 — 老板被叫住的时候，通常只得到一句"客户投诉了，怎么办"。没有影响范围、没有已经做了什么、没有证据、没有可选方案和各自代价。于是老板只能凭经验拍，或者反过来问一圈——而问一圈的时间里，事情继续在恶化。一次没有信息包的升级，等于把判断责任转移给了信息最少的那个人。

核心价值

价值在降级，不在报警

六条上报里两条该降级、两条该合并。把不该占用管理层的摘出去，剩下的才拿得到真资源。全都标红等于全都不红。

重复性靠检索，不靠字段

系统里没有"是否重复"这一列。Agent 去历史记录里按设备号、部位、客户交叉检索——第三次发生的事，性质和第一次完全不同。

归口只建议，并说明排除理由

指派部门是组织权力，Agent 不越权。它给的是"建议归口 X，因为不是 Y 也不是 Z"，理由摆出来，老板一眼能改。

三级分级 · 中小企业只维持得住三级

🔴 P1 紧急 · 2h 响应
已致或将致客户停线 / A 级客户要求升级 / 影响 3 张以上在制工单 / 同一问题第 3 次以上
→ 升 L3 总经理，24h 内出临时方案
🟡 P2 重要 · 当日响应
影响单张工单交期 / B·C 级客户投诉未停线 / 同一问题第 2 次 / 跨 2 个部门
→ 升 L2 部门经理，3 个工作日出方案
🟢 P3 一般 · 3 日响应
客户提醒改进但已验收 / 现场可自行消化 / 首次发生且影响面单一
→ L1 班组自行处理 + 记录归档
为什么是三级而不是四象限矩阵：调研里一个很实在的教训——某企业导入分级初期把 80% 的问题都判成最高级，资源被彻底摊平，真正紧急的反而没人管；后来把最高级压到 15% 左右，满意度反而上升了。级别设计得越复杂，一线越倾向于全部往高的填。三级 + 三层（班组 / 部门 / 老板）是中小企业真正维持得住的粒度。
