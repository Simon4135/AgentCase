产品管理 · 真实业务触发

多币种结算需求（需求池多源收口与语义去重 归一后的那条，证据链 3 家客户 67 万 ARR）过了评审准入，产品经理要在两周后评审会前出 PRD 初稿——背景、目标、功能点、验收标准、竞品现状五段齐全，而且每个功能点的验收标准要写成 验收报告初稿与功能点核对 那种能进合同需求确认书的口径。

三换个做法之后

变化不在「快」，在「参与的角色」和「覆盖的范围」

✕ 现在的做法

  • 每一场需求评审会时长都在 3 小时以上——其中八成时间用于信息对齐（讲背景/对数据/说竞品），留给决策的时间所剩无几
  • PM 每周 12+ 小时用于收集管理反馈——写 PRD 的整块时间被反馈整理切成了碎片
  • 需求变更代价曲线：设计期改 1 倍成本、发布后 100 倍——评审会上没对齐的功能点，代价在后面等着
  • 反馈闭环差的公司浪费最多 35% 开发资源——PRD 里没有证据链的功能点，就是浪费的入口

✓ 交给 Agent 之后

  • 多来源文件一次读入，先做口径与完整性校验，再开始算
  • 每条结论绑定来源文件、字段或条号，可以被审
  • 产出是企业真会流转的正式件（带签批栏），不是一张展示用的表
  • 该拦的地方给出「现在还不能提交」，并给不用干等的替代方案

四场景闭环

5 步 · 每一步的产出都是下一步的输入

第 1 步
证据链回填背景段谁要的、几家客户、多少 ARR、原始表述摘录——每句带出处
第 2 步
功能点拆解按「配置可解决 / 需开发 / 依赖 API 变更」三态拆，API 项联动 API 文档与代码同步巡检 清单
第 3 步
验收标准按合同口径起草每个功能点写成能直接进需求确认书的核对句式
第 4 步
竞品现状引用拼装复用 竞品对比矩阵与讲标弹药 矩阵证据，标注口径等级
第 5 步
评审材料包成稿PRD 初稿 + 预读摘要（评审会前发出）+ 待决策清单

要准备什么

需求池多源收口与语义去重 归一需求与证据链
背景段的事实基础——谁要的、几家、多少 ARR，全带出处
竞品对比矩阵与讲标弹药 竞品对比矩阵（相关能力项）
竞品现状段直接复用，不重新调研
现有功能架构与 API 清单（联动 API 文档与代码同步巡检）
功能点设计的边界——哪些是配置、哪些要动 API
历次评审会的结论与遗留问题
上次评审定过的口径，这次不再重新吵

为什么这个场景值得做

痛感 4 × AI 适配 4 ÷ 落地难度 2 = 8.0

最大差异点 · PRD 不是凭空生成的模板填空：背景段直接引用 需求池多源收口与语义去重 的证据链（3 家客户、4 条原始表述、67 万 ARR），竞品段复用 竞品对比矩阵与讲标弹药 矩阵的公开证据，验收标准按 验收报告初稿与功能点核对 的功能点核对口径写——三个上游场景喂进来的料，让评审会的前 80% 信息对齐时间直接归零。

评分口径：痛感看「这事没做好谁会生气、生气到什么程度」； AI 适配看「输入是否非结构化、是否要跨部门取数、错了能不能当场看出来」； 落地难度是分母 —— 需要客户先做数据治理的场景，分数会被压得很低。

这套东西不承诺什么

PRD 初稿只到「评审版」：功能点取舍、优先级、里程碑由评审会定；验收标准口径对齐合同需求确认书格式，但不替代法务与交付的终审；竞品现状只引用公开来源，口径同 竞品对比矩阵与讲标弹药 三级分级。
