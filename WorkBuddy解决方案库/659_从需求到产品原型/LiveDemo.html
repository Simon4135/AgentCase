1

功能清单 · P0/P1/P2 各归其位

先分级，再动手 —— 评审时优先级有据可依
优先级功能点说明
P0需求解析与功能点提取 / PRD 结构化文档生成 / 高保真原型输出核心链路，缺了就不是这个产品
P1版本对比与迭代优化 / 多格式导出交付评审后迭代提效
P2模板库与历史记录长期沉淀，本期可缓

分级的口径：核心链路先进 P0，提效类进 P1，沉淀类进 P2 —— 评审会上「为什么这个先做」不再靠产品经理现场发挥。

2

PRD 生成 · 六段结构一段不缺

背景 / 故事 / 功能 / 流程 / 数据 / 验收
PRD 段落内容要点
背景高峰等位 20-30 桌，纸质号单 + 人工喊号的现状
用户故事作为产品经理，上传需求文档后自动生成结构化 PRD，节省 70% 撰写时间
功能描述扫码取号 / 进度查询 / 到号提醒 / 过号保留与顺延 / 叫号屏 / 数据看板
验收标准自动识别 ≥90% 核心功能点，支持人工复核

注意验收标准一栏 —— 「做个取号功能」和「≥90% 核心功能点被识别并支持人工复核」之间，隔着 PRD 的全部专业性。

3

高保真原型 · 四页可点，响应式

封面 / 功能清单 / 原型演示 / 导出交付
页面内容评审时怎么用
封面页产品名称、版本号、评审日期开场定调
功能清单页P0/P1/P2 分级列表与状态标签先过优先级
原型演示页可交互页面模拟、响应式切换、评审标注工具栏核心 现场点给区域经理看
导出交付页一键打包下载、在线分享链接、版本管理散会即分发

原型的约束写在 Skill 铁律里：纯净配色（仅 #0052D9 + 中性灰）、文字 ≥16px 留白不贴边、≥3 处点击切换、单文件可离线 —— 评审现场网络不好，也不耽误演示。

PRD 和原型还不能直接交付 —— 两处必须先经产品经理复核
Skill 的重要声明写得很清楚：功能完整性与优先级建议请产品经理复核定稿。两处尤其不能省：

复核点 1 · 业务边界条件：AI 生成的 PRD 可能遗漏业务边界条件 —— 过号保留多久、顺延几桌、提醒失败怎么兜底，须产品经理逐项复核功能清单。
复核点 2 · 原型的定位：HTML 原型不含后端逻辑与真实数据，仅作评审演示 —— 不可直接交给开发当交付物，开发实现须另行排期。

给出的不是「改完再生成一遍」，而是：PRD 结构、功能分级、原型交互直接用，边界条件与交付定位两处处方级把关 —— 复核 15 分钟，比全程手写仍快一个量级，且返工在评审前消化。

追问现场可能被问到的

答不上来的问题，比答得漂亮的问题更能决定这场演示的结果

需求这么模糊也能生成吗？
能，但有边界 —— 需求描述越结构化输出越精准；模糊需求可能要多轮调整才能达标。建议至少补清楚用户角色、核心动作和约束条件。
原型能直接给开发用吗？
不能 —— HTML 原型不含后端逻辑与真实数据，仅作评审演示，不可直接用于开发交付。它的价值是把返工消化在写代码之前。
原型风格能按品牌调性改吗？
可以调整，但 Skill 内置了设计铁律：纯净配色（仅 #0052D9 + 中性灰）、文字 ≥16px、≥3 处可交互、单文件可离线 —— 保证评审演示的稳定与专业感。
