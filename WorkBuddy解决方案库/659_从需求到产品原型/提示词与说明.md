### 一、这件事现在是什么样

*餐饮品牌产品经理 · 评审会前永远在赶稿*

某连锁餐饮品牌，周二下午。运营总监在周会上口头提了个排队叫号的需求 —— 「客人扫码取号、手机上看进度、快叫到微信提醒、过号别直接作废」，前后不到两百字。产品经理要在周五评审会前把这两百字变成一份 PRD：功能点拆出来、优先级排出来、流程画出来、验收标准写出来，光写文档就得两三天。再做出能给区域经理现场点的原型，又是两三天 —— 和设计师来回对齐页面结构，改一版等一版。等评审会真开起来，边界条件没写全，当场被问住，回去返工，下周再审一次。

### 二、痛点 · 每条都发生在昨天

*不是流程描述，是产品团队每周真实上演的日常 —— 以下案例均取自场景调研与演示素材*

1需求是口头的、模糊的：「想要个取号的东西」—— 从一句话到结构化 PRD，光梳理就要两三天

2原型制作与沟通耗时：和设计师来回对齐页面结构，改一版等一版，评审前排期永远不够

3评审返工率高：边界条件没写全、优先级没依据，会上被问住，回去改完下周再审一次

4PRD 和原型是两张皮：文档改了一版，原型忘了同步，开发照着旧原型做，返工从评审拖到了编码

  说明：本场景与现有方案「PRD 一致性终审」的差异 —— 同为 PRD 但方向相反：本场景是从模糊需求生成 PRD 与高保真原型，对方是对已有 PRD 做一致性终审。

### 三、换个做法之后

*变化不在「快」，在「评审前就把返工消化掉」*

✕ 现在的做法
两百字口头需求，产品经理凭经验拆功能点，漏不漏全看状态
PRD 手写两三天，结构一家一个样，验收标准常常缺位
原型等设计师排期，评审前只能拿静态截图讲
会上发现漏了边界条件，回去改文档改原型，下周再审

    ✓ 交给 Agent 之后
上传需求材料，自动识别用户角色、核心功能和边界条件，输出结构化功能清单
基于最佳实践模板生成 PRD：背景/故事/功能/流程/数据/验收六段齐备
同步生成高保真 HTML 可交互原型：响应式布局、评审标注，现场就能点
评审反馈直接迭代 PRD 与原型，输出最终交付版本

### 四、场景闭环

*6 步 · 每一步的产出都是下一步的输入*

第 1 步
解析需求材料 · 自动脱敏解析上传的 .md / .docx / .txt 文件，去除真实客户名称与敏感数据，自动提取功能点清单和优先级
第 2 步
识别功能点 · 角色与边界基于自然语言理解，自动识别用户角色、核心功能和边界条件，生成结构化功能清单
第 3 步
生成 PRD · 六段结构基于最佳实践模板输出结构化 PRD：背景 / 故事 / 功能 / 流程 / 数据 / 验收
第 4 步
生成原型 · 高保真可交互输出高保真 HTML 原型，支持响应式布局和评审标注，单文件可离线演示
第 5 步
评审验证 · 完整性确认基于 PRD 和原型进行需求评审，确认功能完整性和业务逻辑正确性
第 6 步
迭代优化 · 输出交付版根据评审反馈优化 PRD 和原型，输出最终交付版本

    要准备什么
需求材料（.md / .docx / .txt 非结构化需求描述）
口头记录、聊天记录整理均可 —— 越结构化输出越精准

一句话意图（「帮我做 PRD」）
直接说或拖拽文件到对话框

评审约束（评审时间 / 演示设备 / 优先级口径，可选）
有什么给什么 —— 缺项自动按默认口径处理

    为什么这个场景值得做

      痛感 4 × AI 适配 5 ÷ 落地难度 2 = 10.0

      最大差异点 · 一份非结构化需求扔进来，PRD 与可交互原型同时出 —— 评审会上点着原型过需求，返工在写代码之前就消化掉。

      评分口径：痛感看「这事没做好谁会生气、生气到什么程度」；
      AI 适配看「输入是否非结构化、是否要跨渠道取数、错了能不能当场看出来」；
      落地难度是分母 —— 需要先对接 POS/ERP 才能用的场景，分数会被压得很低。

### 五、会产出什么

*判断标准只有一个：这份东西周五评审会能不能直接用*

演示件

  这套东西不承诺什么
产物不含真实后端逻辑，不对接业务 API，不做 VI 设计，不做 ROI 测算；HTML 原型仅作评审演示，不可直接用于开发交付；AI 生成的 PRD 可能遗漏业务边界条件，功能完整性与优先级须产品经理逐项复核定稿；需求描述越结构化输出越精准，模糊需求可能需要多轮调整才能达标。
