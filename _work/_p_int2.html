① Rivian × AWS for SAP —— 为什么财务流程塞不进硬编码脚本

来源：AWS for SAP 官方博客（aws.amazon.com/blogs/awsforsap/…）

Rivian 用 Amazon Bedrock AgentCore 自动化月末/季末结账文档、资源预测与供应商准入。官方博客给出的痛点原文极具代表性：传统自动化（硬编码脚本）解决不了财务流程，因为业务逻辑太动态——PO accruals（采购订单预提）要按金额阈值、PO 特性、交期、GAAP 条件规则去解释 SOP，编码进去可能需要上千行 if-then-else，且业务规则一变就要开发介入。

GenAI Agent 能直接读自然语言 SOP、按情境决策，规则变了不用重写程序。——这正是「文件 + 提示词」路线做不到、而「读系统 + 执行」路线才能做到的事。

同系列另有 Covestro 用 AWS 上 AI Agent 改造主数据治理（Master Data Governance），以及方法论文《Transforming ERP Business Process Operations with Agentic AI》。

② 金蝶云星空 × 灵基（KingdeeMCP）—— 中国 ERP 的实测四场景

来源：金蝶官方社区 vip.kingdee.com/article/879867537130394112（2026-08-25）+ 开源项目 WaHaiLong/KingdeeMCP（110★，Python，97 个工具）

在设置面板添加一个名为 k3cloud 的 MCP 服务器即完成连接，原文称「没有中间件配置，没有接口联调，不需要 IT 部门排期」，连上后拥有直接读写星空 ERP 数据的能力。四个实测场景：

① 查库存 17 秒 ② 查未关闭订单 7 张筛出 2 张 ③ 财务月度分析 22 秒 ④ 审核单据 真的调接口通过

① 问「查一下物料智能手机-6S 的即时库存」→ 自动查到物料编码 S1.06，按仓库分拆（手机成品仓 22 台、电商总仓 98 台，合计 120 台），与星空界面逐行核对分毫不差。
② 问「查询客户金蝶东方集团的所有销售订单有多少张未关闭的」→ Agent 自己摸清关闭状态字段含义（A=未关闭，B=已关闭），筛出 7 张已审核订单、其中 2 张未关闭。
③ 问「统计每月销售额…除了金蝶香港组织，按价税合计本位币计算，每月同比上月增加多少」→ 自动识别组织字段、排除编码 104 的香港公司、保留蓝海销售与蓝海电商，算出 1 月合计 601,186 元与 2 月环比。
④ 说「帮我审核一张费用申请单，申请人是 XXX」→ 查出待审核单据、逐张查看详情锁定李忠声那张 800 元单据、调用审核接口通过，并提示还有一张 500 元待审核。文中还提到它会把 API 调用经验存进记忆，下次不用重新摸索。

技术栈：FastMCP（Python）。这是国内开源生态里与 WorkBuddy 场景最接近、但路线完全相反的样本——同一批业务问题，一边靠导 Excel，一边靠直连 ERP。

③ 制造业 ERP（IQMS / DELMIAworks）—— 一个人做的只读 MCP，一年省 300 小时

来源：haydennester.com/case-studies/iqms-mcp（个人实战记录）

底层 Oracle，系统有 1,500+ 张表。作者 map 了 1,587 张表、2,959 条外键关系，建了一个只读 MCP Server（SSE transport、Oracle python-oracledb、Claude Opus/Sonnet、把 schema 预载入 Agent 上下文、内网部署不外泄）。

覆盖表 1,587 外键关系 2,959 作者自述年省 约 300 小时 ≈ $14K 分析师人力 写权限 设计上为零

把工厂里的问题从「写 SQL 或等厂商报表队列」变成秒级回答。文章还专门解释了「为什么用 MCP 而不是做一个 Text-to-SQL 应用」。

④ Claude 连真实 ERP 记账 —— 「AI 跑在系统记录源里，而不是描述它」

来源：aicoooffice.substack.com（2026-06-24，作者 Joost Vogelezang）

把 Claude 通过 MCP 连到一个叫 CoolERP 的真实 ERP demo。作者强调的三个「不是…而是…」：模型不是总结试算表，而是拉取它；不是描述 COGS 科目，而是下钻；真的过账了一张 journal entry（日记账分录）。

最有说服力的细节是反向验证：故意过一张不平的凭证时，ERP 拒绝接受。作者原话——「AI working inside the system of record with typed, governed tools and full audit visibility」（AI 运行在系统记录源之内，用的是有类型、受治理的工具，全程可审计）。

这个案例说明了可写路线的安全边界在哪里：不是让模型自己保证正确，而是让 ERP 的校验规则挡住错误。

⑨ 一条务实的分档建议：钉钉悟空的 A / B / C 三路线

来源：开沿科技《钉钉悟空 API 接入 ERP 集成》长文（2026-06-14）

文中给了一个 80 人鞋服批发企业的真实翻车现场：开通悟空一个月，销售在群里 @ 悟空问「这个客户上个季度发了多少货」答得头头是道，但只能基于上传的知识库回答，查实时库存、回款、在途订单一概不知。

据此给出的三条路线与选择逻辑：路线 A 原生 Skill 包装（ERP 有标准开放 API 时写薄中间层，投入小上线快，以查询类为主）；路线 B 自定义 Skill 写动作（提交报销、创建客户、生成调拨单——难点在权限、审批流、防误操作，「不能让 Agent 随便代下游员工签字」）；路线 C 反向把 Agent 嵌进自有应用（CRM 详情页右侧放对话区，用户感知在自家系统内完成，对话流可在自家留痕）。

最容易翻车的地方：把所有数据怼进知识库 → 静态文档答得准、动态业务数据全是幻觉。正确分工是静态慢变内容走 RAG（检索增强生成），实时业务数据走结构化查询。

规模参照：McKinsey《The State of AI: Global Survey 2026》——年收入超 10 亿美元的大型组织里，40% 表示正在规模化使用 AI Agent，高于去年的 27%；但小型企业基本持平在 22%。该文与多个分析一致指出：差距来自实施能力，不是软件成本。
