6为什么大部分 Agent 项目卡住：失败的真正原因与安全边界

这一节回答「那为什么不都去做？难在哪？」——也直接解释了 WorkBuddy 为什么要选择外挂路线。

口径必须先分清（否则数字会骗人）

「88%」「89%」「95%」「40%」这些数字经常被混用，但它们测的根本不是同一件事。据 alatirok.com 的逐条溯源：

  • 40% — Gartner：预测到 2027 年底超过 40% 的 agentic AI 项目会被取消。唯一真正针对 Agent 的权威数字
  • 88% / 89% — 多个来源引用的「Agent 试点未进生产」比例，AWS 官网 banner 原文也在用「88% of agent pilots stall」。口径为试点阶段
  • 95% — MIT 的生成式 AI 试点研究，测的是 GenAI 试点而非 Agent。不可直接套用
  • 41% — Stacklok：软件组织中已进入 MCP 生产阶段的比例。正面口径
  • 40% vs 22% — McKinsey 2026：大企业（>10 亿美元营收）规模化使用 Agent 的比例 vs 小企业。能力差距

卡点排序：不是模型不行，是集成不行

  • 第一名：集成。dynamisch.co 直接把文章命名为《The Integration Wall》（集成墙），主张失败主因是集成而非模型能力。
  • 第二名：认证与授权。agent 从「单用户 demo」走向「多用户企业部署」时认证最先崩——原型可以用环境变量或共享 service account，生产必须做委托授权、凭据隔离、策略执行与审计追踪。
  • 第三名：上下文成本。Anthropic 实测 5 个 Server 的工具定义就要吃掉 55K tokens；工具搜索与代码执行等优化可削减 85%–99.9%。GitHub 甚至把自己家的 MCP Server 换成 gh CLI 来做数据抓取。
  • 第四名：权限与「越权代签」。不能让 Agent 随便代下游员工签字——这是写权限路线必须挡住的坑。

认证为什么会先崩：Agent 引入的新身份问题（Arcade.dev《7 Best AI Agent Authentication Platforms (2026)》核心论点）

风险原意后果
Credential drift（凭据漂移）原型期的共享密钥被沿用到生产无法区分「是谁让 Agent 做的这件事」
Confused deputy（混淆代理）Agent 拥有高权限，用户通过间接提示注入借它之手越权AI 成了「有权限但被骗」的执行者 —— 2026 年最被反复讨论的攻击面
过宽 API key一次授权覆盖所有租户/所有动作越权读取、跨系统数据外泄
限流冲突多 Agent 共享同一凭据配额互相挤兑，生产不稳定
策略不一致同一动作在不同入口判定不同审计无法解释
耐久模式：「两个身份 + 委托上下文」。不是给 Agent 一个万能身份，而是同时携带 Agent 身份 与 用户身份，并在运行期评估一个任务级授权上下文（task-specific authorization context），每次动作都取权限交集。
延伸阅读：OWASP 的 MCP Security Cheat Sheet 与 MCP Tool Poisoning 条目；微软 MCP-SECURITY-GATEWAY-1.0 规范；arXiv 2511.20920《Securing the Model Context Protocol (MCP): Risks, Controls, and Governance》——该文把攻击面分成数据驱动（用户生成内容注入、跨系统外泄）、供应链（registry 信任、rugpull 攻击、通过工具描述做上下文投毒）、配置治理（过度授权、动态工具发现）、运行安全（PII 合规、密钥暴露、多 Agent 监控层威胁）四类，并特别提到一类对手：善意但出错的 Agent 自己。

关键判断（请允许我说得直白）：这不是「WorkBuddy 落后」——这是一次刻意的取舍。它把「企业改造」这一项成本从方案里彻底删掉，代价是把「实时、可写、可审计」三项能力也一并删掉了。 对 一个 200 人以下、IT 只有一个兼职、ERP 是五年前买的 的企业来说，这个取舍是对的：外面那套 MCP 集成要 5–15 个工作日 + 身份权限设计，而这套方案当天下午就能跑出结果。 但如果企业已经有 API、有人、有合规要求，那就应该走 MCP 路线，因为「导出 Excel 再上传」在那种环境下反而变成新的风险点——数据副本散落、口径不一致、无审计。
一个可以直接用的判断标准（来自案例③的作者）：如果你的需求是「读」——优先只读 MCP，风险最低收益立竿见影（他靠只读一年省了 300 小时）；如果需求包含「写」——那先问清楚三件事：谁授权、谁来复核、出错谁负责。三个都答不上来，就先别开写权限。

8如果你要往前走一步：按优先级排的行动清单

从「今天就能做」到「需要立项」，按代价从小到大。

第 1 步 · 今天（零成本）

  • 先把 WorkBuddy 的 693 个方案用起来——它是零改造路线的天花板
  • 挑第一个场景：打开 索引.html，按自己的角色筛选，看「最大差异点」是否正好是你的痛点
  • 把「高频、重复、数据基础好」的三条作为选型硬标准

第 2 步 · 本周（验证）

  • 盘一下：你常用系统里哪些有开放 API（金蝶、用友、钉钉、企微、飞书大多有）
  • 装一个 MCP 客户端（Claude / Cursor / Cherry Studio 等），先连一个只读的官方或社区 MCP Server 试手感
  • 读一遍 OWASP 的 MCP Security Cheat Sheet，知道攻击面长什么样

第 3 步 · 本月（试点）

  • 选一个「读多写少」的场景做只读 MCP 试点（参考案例③：先只读，写权限设为零）
  • 老系统没 API？用 AnythingMCP 这类网关把 REST/SOAP/GraphQL/OData/SQL 直接转成工具
  • 为每个 Agent 建立独立身份 + 委托上下文，不要复用共享密钥

第 4 步 · 立项（写权限）

  • 只做「Agent 出草稿 → 人点确认 → 系统执行」的三段式，绝不让 Agent 直接落库
  • 把审批流、权限分级、审计留痕当前置条件而不是后续优化
  • 用系统的校验规则兜底（参考案例④：不平的凭证被 ERP 拒绝）
  • 衡量指标对齐飞鹤那句话：高频、重复、数据基础好、能嵌进流程
